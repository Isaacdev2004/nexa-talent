## Project rules (NexaTalent)
- Public site chrome (header/footer) lives in `src/routes/__root.tsx`; reusable public pieces in `src/components/site/`. Why: one shell for every public page.
- Public jobs are read server-side via `src/lib/jobs.functions.ts` (publishable client) and mapped through the column whitelist in `jobs.mapper.ts`; `PublicJob` must never include a publication date. Why: brief forbids showing publish dates.
- Staff roles are granted only via the service-only `staff_role_grants` table, applied when the matching email is confirmed. Why: no self-assignment of staff roles.
- Demo/sample content must be visibly labelled as demo in the UI. Why: brief forbids presenting invented content as real.
- Design tokens (brand palette, fonts, shadows) live only in `src/styles.css`; components use semantic classes. Why: consistent theming.
- Roles live only in `public.user_roles` (enum `app_role`); checks go through `has_role`/`is_staff` SQL functions. Signup trigger `handle_new_user` may only grant self-service roles (candidate, employer, recruiter, specialist); recruiter/specialist start `pending_review`. Why: prevents privilege escalation.
- Session state comes from `AuthProvider` (`src/hooks/use-auth.tsx`) mounted in `__root.tsx`; signed-in pages live under `src/routes/_authenticated/`. Why: single auth listener and one gate.
- `jobs.published_at` is never granted to anon; staff-only fields (account_status, company verified) are guarded by triggers. Why: business rules from the brief.
- Applications are created only through the `submit_application` SQL function, which validates the job, documents and confirmations and stores profile/job/document snapshots. Documents are immutable (soft-delete only) so snapshots stay valid; candidates may only change an application's status to withdrawn. Why: brief requires historical records not change.
- Candidate files live in the private `candidate-documents` bucket under `<user_id>/…`; open them with short-lived signed URLs. Why: document privacy.
- Forced password change: `profiles.must_change_password` is checked in `_authenticated/route.tsx`; it can only be cleared via the `complete_password_change` SQL function. Why: temporary passwords must be replaced.
- Staff CRM lives under `src/routes/_authenticated/staff/`, gated in its `route.tsx` by the `is_staff` RPC; data access still relies on staff RLS policies. Why: one gate, server-enforced data rules.
- Private job sharing uses `candidate_opportunities` matched by lowercase email; candidates respond only through `respond_to_opportunity`. Why: candidates may not have accounts when a role is shared.
- Audience/info pages render through `src/components/site/MarketingPage.tsx` with a per-page config; simpler pages (resources, FAQ, contact, legal) use `ContentPage`. Why: consistent premium layout without duplicating markup.
- Assessment and specialist mutations use authenticated SQL RPCs; assessment drafts stay staff-only, published reports are immutable, and specialist approvals require administrator roles. Why: enforce review boundaries independently of the browser.
- Specialist services use participant-scoped RLS and authenticated RPCs; candidate consent grants only the exact referred resume, quotation acceptance locks an agreement, and payment confirmation is service-role-only. Why: prevent cross-account disclosure and unpaid work.
- Service deliveries use the private service-deliveries bucket, immutable registered versions and short-lived signed URLs; shared service screens live in ServiceWorkspace. Why: preserve version history and consistent participant workflows.
- Employer workspace lives under `src/routes/_authenticated/employer/`; employer access is scoped by company ownership via `owns_company`/`employer_owns_job`, employers cannot publish (staff approval) and change statuses only through `employer_set_job_status`/`employer_set_application_status`. Why: employers see only their own vacancies and applicants.
